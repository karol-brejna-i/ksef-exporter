# Draft GitHub issue: ksef-client-typescript discards `isTruncated`

*Created: 2026-09-06 18:09 CEST*

Not filed yet — drafted for review. Target repo:
[smekcio/ksef-client-typescript](https://github.com/smekcio/ksef-client-typescript).
Everything from the horizontal rule down is meant to be copy-pasted as the
issue title/body as-is; everything above it is context for whoever decides
whether to file it.

Background for this repo: this gap is what caused the incident documented in
[`design/KSEF_PAGINATION_AND_HASMORE.md`](./KSEF_PAGINATION_AND_HASMORE.md).
We've already worked around it on our side (§7.1 of that doc) by calling the
SDK's own lower-level primitives directly instead of `exportsIncremental.run()`
— that workaround is what proves the suggested fix below is trivial to
implement upstream, since it uses only the library's own already-public
building blocks.

Pinned version at the time of writing: **0.7.1**.

## Suggested title

`IncrementalExportWorkflow.run() computes InvoicePackage.isTruncated internally but never returns it`

## Suggested body

### Summary

`IncrementalExportWorkflow.run()` is the documented, recommended way to do an
incremental invoice export. Internally, on every iteration, it reads
`status.package.isTruncated` — KSeF's own authoritative "is there more data in
this window" signal — and uses it (via `updateContinuationPoint`) to decide
how to advance the continuation point for the *next* iteration. But `run()`'s
return type, `IncrementalExportResult`, does not include `isTruncated` (or
`lastPermanentStorageDate` / `permanentStorageHwmDate`) anywhere. The value is
computed, used internally, and discarded before the caller ever sees it.

Any application doing its own incremental/paginated sync on top of `run()`
(e.g. "fetch a page now, and decide later whether to fetch another") has no
way to ask "was the page I just got truncated, or is this genuinely
everything available right now?" — despite the SDK having already computed
that exact answer one line earlier.

### Where this lives in the source

`services/incrementalExportWorkflow.ts`, inside the iteration loop:

```ts
updateContinuationPoint(options.continuationPoints, options.subjectType, status.package ?? {}, {
  dateType: filters.dateRange?.dateType,
});
```

`services/hwmCoordinator.ts`'s `updateContinuationPoint` reads exactly the
field we need, then throws it away:

```ts
const isTruncated = Boolean(packageInfo.isTruncated);
const lastPermanentStorageDate = packageInfo.lastPermanentStorageDate ?? undefined;
const hwmDate = packageInfo.permanentStorageHwmDate ?? undefined;
if (isTruncated && lastPermanentStorageDate) {
  continuationPoints[subjectType] = lastPermanentStorageDate;
  return;
}
if (hwmDate) {
  continuationPoints[subjectType] = hwmDate;
  return;
}
delete continuationPoints[subjectType];
```

And the return type that never gets it back out:

```ts
export interface IncrementalExportResult {
  referenceNumbers: string[];
  metadataSummaries: Array<Record<string, unknown>>;
  invoiceXmlFiles: Record<string, string>;
  continuationPoints: ContinuationPoints;
  // no isTruncated, no lastPermanentStorageDate, no permanentStorageHwmDate
}
```

### Reproduction

```ts
const result = await client.workflows.exportsIncremental.run({
  subjectType: "Subject2",
  windowFrom: "2026-08-01",
  windowTo: "2026-09-06",
  continuationPoints: {}, // or a previously-persisted one
  maxIterations: 1,
});

// result = { referenceNumbers, metadataSummaries, invoiceXmlFiles, continuationPoints }
//
// Nothing in `result` says whether the fetched page was truncated (more data
// exists in this window right now) or genuinely exhausted (isTruncated was
// false). A caller building "should I call this again?" logic is forced to
// either:
//
//   (a) reimplement run()'s own start->wait->download->updateContinuationPoint
//       loop itself against the lower-level primitives, purely to recover the
//       one field that's missing, or
//
//   (b) guess from `result.continuationPoints`' timestamp -- which is
//       unreliable, because when isTruncated is false the continuation point
//       becomes `permanentStorageHwmDate`, generated by the server at
//       export-init time. By the time the caller reads its own clock after
//       the full start/poll/download/decrypt round trip, that HWM is already
//       some seconds-to-minutes in the past relative to "now" -- in our
//       production data, consistently ~120 seconds, every single call, in
//       both of our test tenants. Any heuristic built on "close to now" or
//       "advanced since last time" is defeated by this gap and can report
//       "more data available" forever on pages that returned zero invoices.
```

### Impact

We hit this in production: a historical backfill tool built on `run()`'s
result kept re-triggering `POST /invoices/exports` (a request that's
rate-limited to 16/min, 20/hour per subject type) on calls that fetched zero
invoices, because there was no way to distinguish "truncated, fetch again"
from "exhausted, stop" other than the unreliable timestamp heuristic above.
Full writeup, including real measured gaps from two production tenants:
[`design/KSEF_PAGINATION_AND_HASMORE.md`](./KSEF_PAGINATION_AND_HASMORE.md) in
our repo (kbrejna/ksef-exporter — happy to link once/if that repo is public,
otherwise we can paste the relevant section into the issue).

### Suggested fix

Add the already-computed fields to `IncrementalExportResult`, purely
additive/optional so it's non-breaking:

```ts
export interface IncrementalExportResult {
  referenceNumbers: string[];
  metadataSummaries: Array<Record<string, unknown>>;
  invoiceXmlFiles: Record<string, string>;
  continuationPoints: ContinuationPoints;
  /** From the *last* iteration's status.package, before it's discarded. */
  isTruncated?: boolean;
  lastPermanentStorageDate?: string | null;
  permanentStorageHwmDate?: string | null;
}
```

populated from the last iteration's `status.package` right before `run()`
returns. An even simpler alternative that's forward-compatible with any future
`InvoicePackage` fields:

```ts
export interface IncrementalExportResult {
  // ...existing fields...
  /** The last package status seen, verbatim, for callers that need more than continuationPoints alone. */
  lastPackage?: InvoicePackage;
}
```

Either shape is a small, low-risk change — the value already exists in scope
at the exact line quoted above; this only asks that it survive to the return
statement.

### Workaround we're using meanwhile

We bypassed `exportsIncremental.run()` entirely and call the same
lower-level pieces it already calls internally, all of which are already
public: `client.workflows.exports.startExport()` /
`.waitForExport()` / `.downloadAndProcessPackage()`, plus the three exported
helpers `run()` itself uses between iterations —
`updateContinuationPoint`, `getEffectiveStartDate`, `dedupeByKsefNumber`
(all re-exported from the package root). We replicated `run()`'s loop
algorithm almost verbatim and just kept `status.package.isTruncated` /
`lastPermanentStorageDate` / `permanentStorageHwmDate` from the final
iteration before returning.

This works fine and needs no SDK change to keep working, but it means every
consumer who needs correct "is there more" semantics has to reimplement
`run()`'s loop themselves, and has to keep that reimplementation in sync with
any future changes to the real `run()`'s algorithm. Exposing the field
directly would let us (and presumably other users) go back to calling
`run()` as intended.
